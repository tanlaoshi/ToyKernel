# ToyOS 开发命名规范

> **本文是 ToyOS 所有代码的命名约束。** 新增代码必须遵守；旧代码逐步迁移。
>
> 相关文档：
> - [`技术手册.md`](../技术手册.md) — 分层与接口（§I）；库与 GUI 见 §IV
> - [`路线图.md`](../路线图.md#五c-标识符命名规划) §五 — C 标识符命名规划（历史迁移清单）

---

## 一、总则

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| **PascalCase** | 每个单词首字母大写，单词之间无下划线 |
| **全词拼写** | 不缩写、不省略（`Configure` 不是 `Cfg`） |
| **类型全大写** | 结构体、枚举、宏用 `ALL_CAPS` |
| **全局 `g` 前缀** | 全局变量用 `g` + PascalCase |
| **静态 `s` 前缀** | 文件内静态变量用 `s` + PascalCase（可选） |
| **分层前缀在最前** | `Hal` / `Toy` / `Kernel` / `Board` 等统一层名写在标识符**最前面** |
| **名词在前、动词在后** | 层前缀之后：`SerialWrite`，不是 `WriteSerial`（**新代码强制**；旧代码不顺手大搬） |
| **新模块 >300 行即拆** | 主文件保留模块名（如 `Console.c`）；辅助能力另文件（如 `ConsoleWrite.c`） |
| **日志文案跟标识符** | 串口/屏上日志：单词 **PascalCase**；缩写 **ALL_CAPS**（`COM1`/`GOP`/`ELF`/`USB`）；前缀用 `Boot:` / `[Mod]`，勿 `boot:` / `[mod]` |

**日志示例**（新/改动的 bring-up 文案必须如此；旧 `boot:` 存量逐步迁）：

| 正确 | 错误 |
|------|------|
| `Boot: GetAndSetVideo` | `boot: GetAndSetVideo` |
| `Boot: GOP Cleared 1920x1080` | `boot: gop cleared 1920x1080` |
| `COM1 Serial OK` | `[COM1]:初始化OK` / `com1 serial ok` |
| `[Mod] VirtualMemory` | `[mod] virtual-memory` |

### 1.2 为什么这样

| 理由 | 说明 |
|------|------|
| **可读性** | PascalCase 在英文中更接近自然语言 |
| **搜索友好** | 全词拼写让 `grep Configure` 能找到所有相关代码 |
| **与 EDK2 一致** | UEFI 参考实现用 PascalCase，ToyOS 也走这条路 |
| **避免缩写歧义** | `Cfg` 可能是 Configure / Config / Configuration，全词避免歧义 |

### 1.3 现状（2026-09 抽样）

内核公开头（`Include/*.h`）与 `Core/`、`HAL/X64/`（不含 LwIP）的函数几乎全部是 **PascalCase**。抽样未见内核 API 用 snake_case / camelCase。

`HAL/X64/LwIp/` 是第三方：允许 `sys_now` 等原项目风格，不按本规范改。

**明确例外（保持，不迁成 PascalCase）**：

- POSIX / CRT：`User/include/*.h`、`User/crt/` 的 `fopen` / `malloc` / `lseek` / `stdio.h` / `user.ld` / `crt0.S`
- 脚本：`build.sh`、`Tools/build-sdk.sh`（kebab-case）
- FAT 盘上产品名：`MYAPP.ELF` 等 8.3 大写

## 二、函数命名

### 2.1 基本规则

```
[分层前缀?] + 名词（子系统/对象）+ 动词（[+ 宾语]）（PascalCase）
```

1. **统一层名在最前**：`Hal` / `Toy` / `Kernel` / `Board` / `ToyDriver` 等写在标识符开头（无层前缀的模块则直接从名词起，如 `ConsoleWrite`）。
2. **名词在前、动词在后**：层前缀之后先写对象/子系统，再写动作。正确：`SerialWrite`、`HalSerialWrite`；错误：`WriteSerial`、`HalWriteSerial`。
3. **旧代码**：已存在的 `WriteSerial` / `InitializeSerial` 等**不**为本规则强制翻库；**往后新写的符号必须遵守**。改到某文件时允许顺手改同文件内明显违规名（见 §八）。

**示例**：

| 正确（新代码） | 错误 |
|----------------|------|
| `HalSerialWrite` | `HalWriteSerial` / `WriteSerial` / `hal_serial_write` |
| `SerialInitialize` | `InitializeSerial` / `InitSerial` / `SerialInit` |
| `ConsoleWrite` | `WriteConsole` |
| `ToyDriverRegister` | `RegisterToyDriver`（层前缀须最前） |
| `VirtualMemoryMapPage` | `MapVirtualMemoryPage`（子系统名词块在前） |
| `FatReadFile` | `ReadFatFile`（在 Fat 模块内动词抢前） |

### 2.2 分层前缀

| 层 | 前缀（须最前） | 示例 |
|----|----------------|------|
| **HAL** | `Hal*` | `HalSerialWrite` / `HalVideoFillRect` |
| **驱动框架** | `ToyDriver*` | `ToyDriverRegister` / `ToyDriverProbeAll` |
| **Core** | 无前缀或 `Kernel*` | `KernelMain` / `SchedulerCreate` |
| **Library** | 无前缀 | `FatReadFile` / `GptFindFatStart` |
| **Services** | 无前缀 | `ConsoleWrite` / `GuiOpenShell` |
| **用户态库** | `Toy*` | `ToyUiCreateWindow` / `ToyGfxDamageRect` |
| **Board** | `Board*` | `BoardInitialize` / `BoardName`（新代码勿再 `BoardInit`） |

### 2.3 常用动词

| 动词 | 用途 | 示例（名词+动词） |
|------|------|-------------------|
| `Initialize` | 初始化 | `SerialInitialize` / `HalSerialInitialize` |
| `Configure` | 配置 | `InterruptConfigure` |
| `Register` | 注册 | `ToyDriverRegister` |
| `Attach` | 挂载 | `ToyDriverInputAttach` |
| `Probe` | 探测 | `XhciDriverProbe` |
| `Bind` | 绑定 | `XhciDriverBind` |
| `Remove` | 移除 | `XhciDriverRemove` |
| `Read` / `Write` | 读写 | `FatReadFile` / `HalSerialWrite` |
| `Get` / `Set` | 存取 | `ThemeSetFontId` / `HalCpuGetId`（新代码）；历史 `HalGetCpuId` 不强制翻 |
| `Allocate` / `Free` | 分配/释放 | `PhysicalMemoryAllocatePages` |
| `Create` / `Destroy` | 创建/销毁 | `SchedulerCreate` / `WindowDestroy` |
| `Open` / `Close` | 打开/关闭 | `FileSystemOpen` / `ConsoleClose` |
| `Enable` / `Disable` | 启用/禁用 | `HalIrqEnable` / `HalIrqDisable` |
| `Start` / `Stop` | 启动/停止 | `SchedulerStart` / `TimerStop` |
| `Load` / `Store` | 加载/存储 | `ElfLoadFromMemory` / `DbSet` |
| `Parse` / `Format` | 解析/格式化 | `FatParsePath` / `HalSerialFormatHex` |
| `Handle` | 处理 | `InterruptHandle` |
| `Dispatch` | 分发 | `SyscallDispatch` |
| `Poll` | 轮询 | `XhciInputPoll` |
| `Flush` | 刷新 | `BlockFlush` |

历史模块入口以 `*Initialize` 为正统（`FileSystemInitialize` / `HalSerialInitialize` / `VirtualMemoryInitialize`）。**新增**入口用 **名词+`Initialize`**（如 `SerialInitialize`），禁止 `InitializeSerial` / `SerialInit`。余下短名按 [`路线图.md`](../路线图.md#五c-标识符命名规划) §五 / 已收官 R 柱再统一。

### 2.4 返回类型与命名约定

| 返回类型 | 命名提示 | 示例 |
|----------|----------|------|
| `int`（成功 0，失败负） | 无特殊 | `FatReadFile` |
| `int`（成功 1，失败 0） | 加 `Is` / `Has` / `Can` | `IsDirectory` / `HasEvent` |
| `void` | 加动作动词 | `ConsoleWrite` |
| 指针 | 加 `Get` / `Create` / `Allocate` | `GetCurrent` / `CreateWindow` |
| 布尔 | 加 `Is` / `Has` / `Should` | `IsReady` / `HasData` |

### 2.5 POSIX / CRT 例外

用户态 Unix 兼容层**保持小写 + 下划线**，与主机 libc 对齐，**不**改成 PascalCase：

```c
int open(const char *path, int flags);
FILE *fopen(const char *path, const char *mode);
void *malloc(size_t n);
off_t lseek(int fd, off_t offset, int whence);
```

ToyOS 自有库仍用分层前缀：`ToyUiCreateWindow`、`ToyGfxDamageRect`、`ToyNetResolve`。

## 三、变量命名

### 3.1 局部变量

```
PascalCase（循环短名除外）
```

**推荐**：局部变量与函数参数用 **PascalCase**：

```c
void ProcessData(int BufferSize, char *InputBuffer) {
    int Index;
    int Count;
    char *Pointer;

    for (Index = 0; Index < BufferSize; Index++) {
        Count++;
    }
}
```

**允许的简写**：仅少数约定俗成的短名：

- `i` / `j` / `k`（循环索引，仅限简单循环）
- `x` / `y` / `z`（坐标，仅限几何）
- `fd`（文件描述符）
- `id`（标识符）
- `pid`（进程 ID）

### 3.2 全局变量

```
g + PascalCase
```

**示例**：
| 正确 | 错误 |
|------|------|
| `gCommands` | `commands` / `g_commands` |
| `gDriverCount` | `gDrvCnt` |
| `gSchedulerLock` | `gSchedLock` |
| `gActiveWindow` | `gActiveWin` |

现码短名已按 R 柱写全（如 `gCommandCount`、`gSaveWidth`）；新增全局继续全词。

### 3.3 静态变量

```
s + PascalCase（可选）
```

**示例**：
```c
static int sInitialized;
static UINT32 sBuffer[1024];
```

**注**：也可以用无前缀的 PascalCase。文件内 `static` 优先 `s`；跨文件可见用 `g`（现码里不少 `static` 仍用 `g`，如 `gRunq`，不强制一次改完）。

### 3.4 指针变量

```
PascalCase，无需特殊前缀
```

**示例**：
```c
char *Buffer;
TOY_DRIVER *Driver;
HAL_INTERRUPT_FRAME *Frame;
```

**不要用**匈牙利命名法（`pBuffer` / `lpDriver`）。

### 3.5 常量

```
ALL_CAPS（宏）或 const PascalCase
```

**宏**（推荐）：
```c
#define MAX_TASKS 8
#define FAT_OK 0
#define PORTSC_CCS (1u << 0)
```

**const 变量**（可选）：
```c
static const UINT32 DefaultWindowWidth = 400;
static const char *const DefaultFontName = "Terminus16x32";
```

## 四、类型命名

### 4.1 结构体

```
ALL_CAPS（下划线分隔）
```

**示例**：
```c
typedef struct {
    ...
} TOY_DRIVER;

typedef struct {
    ...
} HAL_INTERRUPT_FRAME;

typedef struct {
    ...
} FAT_DIRECTORY_ENTRY;
```

**对比**：Linux 用 `struct toy_driver`，ToyOS 用 `TOY_DRIVER`。

用户态自有类型同样 ALL_CAPS（`TOY_GFX_DAMAGE_RECT`、`TOY_DIR`）。**不要**再新增 `ToySockAddrIn` 这种 PascalCase typedef；旧名按 §八 迁移。

### 4.2 枚举

```
ALL_CAPS 类型名 + ALL_CAPS 成员
```

**示例**：
```c
typedef enum {
    TOY_DRIVER_CLASS_NONE = 0,
    TOY_DRIVER_CLASS_BLOCK,
    TOY_DRIVER_CLASS_INPUT,
    TOY_DRIVER_CLASS_NET,
    TOY_DRIVER_CLASS_DISPLAY
} TOY_DRIVER_CLASS;

typedef enum {
    GUI_WIN_NONE = 0,
    GUI_WIN_SHELL,
    GUI_WIN_SETTINGS,
    GUI_WIN_FILES
} GUI_WIN_KIND;
```

### 4.3 typedef

```
ALL_CAPS（与结构体、枚举一致）
```

**示例**：
```c
typedef UINT64 PHYSICAL_ADDRESS;
typedef UINT32 PROCESS_ID;
```

POSIX 头例外：`FILE`、`size_t`、`off_t` 保持 Unix 惯用名。

## 五、宏命名

### 5.1 常量宏

```
ALL_CAPS（下划线分隔）
```

**示例**：
```c
#define MAX_TASKS 8
#define PAGE_SIZE 4096
#define FAT_ENT_NAME_MAX 64
#define PORTSC_CCS (1u << 0)
```

### 5.2 函数宏

```
ALL_CAPS 或 PascalCase（视复杂度）
```

**简单的函数宏**（推荐 ALL_CAPS）：
```c
#define ALIGN_UP(x, a) (((x) + (a) - 1) & ~((a) - 1))
#define MIN(a, b) ((a) < (b) ? (a) : (b))
```

**复杂的函数宏**（推荐 PascalCase，模拟函数）：
```c
#define ListForEach(Entry, List) \
    for ((Entry) = (List)->Head; (Entry); (Entry) = (Entry)->Next)
```

**优先用函数**：如果可以用 static inline 函数代替，就不要用宏。

### 5.3 编译开关

```
TOY_* 前缀
```

**示例**：
```c
#define TOY_DEBUG 1
#define TOY_DEMO_DRIVER 1
#define TOY_USB_MSC 1
```

**编译命令**：
```bash
./build.sh TOY_DEBUG=1 TOY_DEMO_DRIVER=0
```

## 六、文件命名

### 6.1 源文件

```
PascalCase.c / PascalCase.h
```

**示例**：
| 正确 | 错误 |
|------|------|
| `VirtualMemory.c` | `virtual_memory.c` / `vmm.c` |
| `PhysicalMemory.c` | `pmm.c` |
| `FileSystem.c` | `filesystem.c` / `fs.c` |
| `Scheduler.c` | `sched.c` |
| `XhciCore.c` | `xhci_core.c` |

**例外**（保持现状）：

- `crt0.S` / `syscall.S`（CRT 惯例）
- `user.ld`（链接脚本惯例）
- `User/include/stdio.h` 等 POSIX 头（小写）
- `build.sh` / `Tools/build-sdk.sh`（脚本 kebab-case）

### 6.3 新模块行数与拆分（≤300 · 1 核心 + 多辅助）

**规则**（**新写模块 / 新 `.c` 强制**；存量大文件按 [`../Done/大文件拆分3.md`](../Done/大文件拆分3.md) 排队，不因本条立刻翻库）：

1. 单文件（`.c` 实现）**不得超过约 300 行**；将满或明显继续膨胀时**先拆再写**，禁止继续堆在同一翻译单元里「再写一截」。
2. **拆分形态固定为：1 个核心文件 + 多个辅助文件**（不是「随便切两半」）。
3. **核心文件**用模块名：如 `Console.c`（入口、表、生命周期、对外薄封装）。
4. **辅助文件**按能力/主题切：如 `ConsoleWrite.c`、`ConsoleScroll.c`、`ConsoleCmd.c`；对外可经 `ConsolePrivate.h` 或模块公开头衔接。
5. 拆分原则与历史轨一致：**只搬家、不改行为**；对外 API 语义不变。
6. 命名：辅助文件名 = 模块名 + 能力名词（PascalCase），与 §2.1「名词在前」一致（`ConsoleWrite` 文件承载 write 相关实现）。
7. 路线图强制入口：[`路线图.md` 〇·代码原则](../路线图.md#sec-0-code)。

**示例**：

| 核心文件 | 辅助文件（示例） |
|--------|------------------|
| `Console.c` | `ConsoleWrite.c` / `ConsoleScroll.c` / `ConsoleCmd.c` |
| `GuiWm.c` | `GuiHit.c` / `GuiOpen.c` / `GuiPointer.c`（既有模式） |
| Boot 串口（新） | `Boot.c` + `BootSerial.c`（若串口逻辑膨胀） |

### 6.4 目录

```
PascalCase/
```

**示例**：
| 正确 | 错误 |
|------|------|
| `Core/` | `core/`（勿再塞进 `Common/`） |
| `HAL/X64/` | `hal/x64/` |
| `User/Library/ToyUi/` | `user/library/toyui/` |
| `User/Pkg/` | `user/pkg/` |
| `User/Apps/` | `user/apps/` |
| `Drivers/XHCI/` | `drivers/xhci/` |
| `Tools/Sdk/Examples/Hello/` | `tools/sdk/examples/hello/` |

**例外**：

- `HAL/`（全大写，与 EDK2 一致）
- `X64` / `Arm64` / `RiscV`（架构名；`RiscV` 目录保持现状，不改 `RiscV64`）
- `Virt/`（虚拟平台）

### 6.5 脚本与命令行产物

```
kebab-case（仅 *.sh 与仓库根构建入口）
```

**示例**：`build.sh`、`Tools/build-sdk.sh`、`Tools/check-naming.sh`（若将来增加）。

FAT 根上的 ELF **仍是 8.3 大写**（`HELLO.ELF`），与源码目录名无关。

## 八、迁移策略

### 8.1 新代码

**必须**遵守本规范（含 §2.1 词序、§6.3 行数拆分）。

### 8.2 旧代码

**逐步迁移**，不强制一次改完。迁移原则：

1. **改代码时顺手改**：修改某个函数时，把该文件内的旧命名改为新命名
2. **不跨文件改名**：一次 PR 只改一个模块的命名
3. **改名前先冻结接口**：如果符号是对外 API，先讨论再改
4. **每次迁移独立 PR**：便于 review 和回滚

### 8.3 已知的历史遗留

## 十一、常见问题

### Q1: 为什么不用 snake_case？

**A**:

- PascalCase 与 EDK2 一致（UEFI 参考实现）
- PascalCase 在英文中更接近自然语言
- ToyOS 现有内核代码已经大量使用 PascalCase
- 用户态 POSIX 符号仍用 snake_case（见 §2.5）

### Q2: 为什么类型用 ALL_CAPS？

**A**:

- 与 EDK2 一致（`EFI_FILE_PROTOCOL`）
- ALL_CAPS 让类型在代码中一目了然
- 与变量区分（变量 PascalCase，类型 ALL_CAPS）

### Q3: 为什么全局变量加 `g` 前缀？

**A**:

- 一眼看出是全局变量
- 避免与局部变量混淆
- 与 EDK2 一致（`gBS` / `gImageHandle`）

### Q4: 缩写白名单怎么定？

**A**:

- 只保留**公认缩写**（如 CPU / USB / PCI）
- 不保留**可写全的缩写**（如 Init → Initialize）
- 有歧义的缩写写全（如 Cfg → Configure / Configuration）

### Q5: 旧代码什么时候改？

**A**:

- 不强制一次改完
- 改代码时顺手改
- 每次迁移独立 PR
- 参考 [`路线图.md`](../路线图.md#五c-标识符命名规划) §五

### Q6: 为什么是「名词 + 动词」而不是「动词 + 名词」？

**A**:

- 同一子系统下符号自然聚在一起：`SerialInitialize` / `SerialWrite` / `SerialRead`，grep `Serial` 即可扫全
- 层前缀（`Hal`）固定最前之后，名词块标识「改谁」，动词标识「做什么」：`HalSerialWrite`
- **仅约束新代码**；历史 `InitializeSerial` / `HalGetCpuId` 等不因本条翻库

### Q7: 新模块为什么 ≤300 行就要拆成「1 核心 + 多辅助」？

**A**:

- 与既有大文件拆分门槛一致（见 [`../Done/大文件拆分3.md`](../Done/大文件拆分3.md)）
- **1 核心 + 多辅助**：核心保留模块入口，辅助按能力切开（`Console.c` + `ConsoleWrite.c`），对齐既有 `GuiWm`/`Desktop` 拆法
- **新写模块**超标必须拆；存量大文件走拆分轨，不借本规范瞬间大搬家
- 路线图强制入口：[`路线图.md` 〇·代码原则](../路线图.md#sec-0-code)
