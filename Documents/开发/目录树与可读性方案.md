# ToyOS 目录树与可读性方案（草案）

> **状态**：草案。只谈结构与命名怎么排、怎么读；**不**在本文开刀改树。  
> **配套**：[`代码可读性规范.md`](代码可读性规范.md)（主函数顺序表）、[`开发命名规范.md`](开发命名规范.md)、[`../待做/人民可读代码.md`](../待做/人民可读代码.md)（人话文件头）。  
> **目标一句话**：打开 ToyOS，**目录按字母排出来的顺序 = 从开发到编译到运行的故事**；打开任何一个 `.c`，**名字和分层告诉你它是干什么的**。  
> **原则**：逐步完善细节；改树是大手术，先钉方案再拆 PR。

## 0. 问题陈述

现状（2026-10）顶层大致是：

```text
ToyOS/
  Build/          ← 产物
  Config.txt
  EDK2/           ← 第三方
  Scripts/
  ToyBoot/
  ToyImage/
  ToyKernel/
```

按字母排：`Build` 最先、`ToyBoot` 在 `ToyImage` 前、`ToyKernel` 最后——**和「先 Boot → 再 Kernel → 再 Build → 再 Image」的故事相反**。  
Kernel 内用 `CodeA-HAL` … `CodeE-User` 表达依赖顺序，能排，但 **CodeA 不像人话**，外人不知道 A 是什么。  
人话头（人民可读）刚铺了几个入口样板，**树本身仍不像说明书**——这才是「差很远」的根。

本文要钉的是：**树怎么排、层怎么叫、文件怎么拆、名字怎么自说明**；并附外部分案供对照。原文需求见文末 §9。

## 1. 总原则（先钉死）

| # | 原则 | 含义 |
| - | ---- | ---- |
| P1 | **排序即故事** | 资源管理器「按名称」时，从上到下应是：文档/脚本（可选）→ Boot → Kernel → Build → Image |
| P2 | **前缀表达顺序，词表达含义** | 字母序不够时用数字/阶段前缀；前缀后面仍是完整英文词，不用 `CodeA` |
| P3 | **架构只在该分的地方分** | Boot、HAL：按 arch 分子目录；Library / Core / Services / User：**不分 arch** |
| P4 | **依赖向下、调用向上** | 下层不依赖上层；目录序号小的更「底」、更先初始化 |
| P5 | **主文件编排，辅文件干活** | 每模块一个主 `.c`（小）+ 若干辅 `.c`；主文件排最前 |
| P6 | **一文件一职责、一函数一事** | 过大则按「主名 + 能力」拆；拆名仍能被字母序读懂 |
| P7 | **名字自说明** | 文件/函数/变量不怕长；带模块归属；禁暗号缩写（沿用命名规范） |
| P8 | **文档与脚本统一入口** | `Documents`、`Scripts` 各一处；与 Boot/Kernel 同级（细节待定） |
| P9 | **零行为迁移** | 改树/改名的刀与改功能的刀分开；先文档后搬 |
| P10 | **换文件夹 = 换实现** | 契约在公开头 / `*_OPS`；Class→Protocol→Family→Chip 与政策实现各住其夹，不与上层混写 |
| P11 | **上层不知具体芯片** | Core / Services 只认 Class/契约；Chip 名与 quirks 只出现在第 3/4 层 |

> **模块化专章**：四层驱动（Class→Protocol→Family→Chip）与横切契约 → **[§15](#15-模块化契约与四层驱动模型草案)**。

## 2. 第一层：ToyOS 根目录

### 2.1 期望阅读顺序（故事线）

| 序 | 阶段 | 人话 | 今日近似 |
| -- | ---- | ---- | -------- |
| 1 | 读懂 / 协作 | 文档、脚本（怎么开工） | `ToyKernel/Documents`、根/`Scripts`、零散 |
| 2 | 开发 · Boot | 固件/引导，按架构 | `ToyBoot` |
| 3 | 开发 · Kernel | 内核与用户态源码 | `ToyKernel` |
| 4 | 编译产物 | 中间产物、ELF | `Build` |
| 5 | 运行镜像 | 可刷盘 / QEMU 用的根文件系统与 ESP | `ToyImage` |
| — | 第三方 | EDK2 等，不进主故事 | `EDK2` |

### 2.2 候选命名（待决）

字母序要等于故事序，**裸名 `Boot`/`Build`/`Kernel`/`Image` 排不成**（`Build` 会冲到最前）。必须加**阶段前缀**。

**方案 A — 两位数字前缀（推荐作默认讨论稿）**

```text
ToyOS/
  00-Documents/          # 或仍叫 Documents，见 §7
  01-Scripts/
  10-Boot/
  20-Kernel/
  30-Build/
  40-Image/
  90-ThirdParty/         # EDK2 等
  Config.txt
  README.md
```

- 优点：任意资源管理器按名排序即故事；数字档位留空（15-…）可插层。  
- 缺点：路径变长；旧脚本/`build.sh` 要跟迁；Git 历史大挪。

**方案 B — 阶段词前缀**

```text
Dev-Boot/
Dev-Kernel/
Out-Build/
Out-Image/
Doc-Documents/
Tool-Scripts/
```

- 优点：比纯数字更「人话」。  
- 缺点：`Dev-` / `Out-` 两套前缀，新人要记分类词。

**方案 C — 不改目录名，用根 README「地图」+ 符号链接**

- 优点：迁移成本低。  
- 缺点：**不满足**「按字母排就是三阶段」——排除作终态，可作过渡。

**本稿默认按方案 A 往下写**；定案前不改仓库。

### 2.3 与现仓对照（不迁，只对照）

| 现名 | 方案 A 目标名 | 备注 |
| ---- | ------------- | ---- |
| `ToyBoot` | `10-Boot` | 去掉 Toy 前缀以免三仓都 Toy 重复 |
| `ToyKernel` | `20-Kernel` | 文档是否抽出见 §7 |
| `Build` | `30-Build` | 可继续 gitignore |
| `ToyImage` | `40-Image` | |
| `EDK2` | `90-ThirdParty/EDK2` | 或保留顶层 `90-EDK2` |
| `Scripts` | `01-Scripts` | 与 Kernel 内 Tools/Scripts 合并策略见 §7 |
| `Config.txt` | 留根 | 全局旋钮 |

多仓（ToyKernel / ToyImage / ToyBoot 各一 git）是否合并为单仓：**另开议题**，本方案先假定「逻辑树」长这样，物理仓边界可后钉。

## 3. 第二层：Boot 与 Kernel

### 3.1 Boot：按架构分

```text
10-Boot/
  README.md
  X64/          # 或 Ia32/X64 再议；现树以 X64 为主
  Arm64/
  RiscV/
  # Mips / LoongArch … 目录可先占位或暂不建
  Common/       # 可选：三架构共用的纯逻辑（若几乎没有则可省略）
```

每个 arch 目录内：该架构引导所需的 `.c` / `.h` / `.inf` / `.dsc` / 链接脚本等。  
**不支持的架构**：不建目录，或只放 `README.md` 写「未支持」，避免空壳误导。

### 3.2 Kernel：按执行 / 依赖分层（取代 CodeA…E）

今日：`CodeA-HAL` → `CodeB-Library` → `CodeC-Core` → `CodeD-Services` → `CodeE-User`。  
意图对，**前缀词不对**。

**推荐：数字 + 全词层名**

```text
20-Kernel/
  10-Hal/              # 原 CodeA-HAL
  20-Library/          # 原 CodeB-Library（被 Core 依赖 → 序在 Core 前）
  30-Core/             # 原 CodeC-Core + 可替换 Modules 是否并列见下
  40-Services/         # 原 CodeD-Services
  50-User/             # 原 CodeE-User
  Include/             # 公开头；或打散到各层（待决）
  Modules/             # 原 CodeC-Modules 学生可替换件；见 §3.3
  ThirdParty/          # 内核内第三方
  build.sh
  Makefile
```

字母序：`10-Hal` < `20-Library` < `30-Core` … **Core 不会再排到 Library 前面**——这直接回应需求 §4。

**不推荐继续用 `CodeA`**：字母只表达顺序，不表达「这是 HAL」。

### 3.3 可替换模块（学生调度器 / 分配器 / FS）放哪

| 选项 | 形状 | 说明 |
| ---- | ---- | ---- |
| M1 | `30-Core/Modules/Student/…` | 紧贴 Core，依赖清晰 |
| M2 | `35-Modules/` 与 Core 并列 | 强调「可替换柱」，序号插在 Core 与 Services 之间 |
| M3 | 维持今日 `CodeC-Modules` 语义，仅改名前缀 | 迁移最小 |

**讨论默认：M2 `35-Modules/`**——课堂作业入口一眼看得见，又不假装是 HAL。

## 4. 第三层：Hal 按架构；其余架构无关

### 4.1 Hal

```text
10-Hal/
  X64/
  Arm64/
  RiscV/
  Include/          # 可选：Hal 对外的薄接口；或统一走 Kernel/Include/Hal
```

- 驱动、启动汇编、板级、串口/时钟等 **因 arch 而异** 的放进对应目录。  
- **禁止**在 `20-Library` 及之后再按 X64/Arm64 分裂一份拷贝。

### 4.2 Library / Core / Services / User

不分架构。若某文件暂时只能在一架构编译：用 `#if` / Makefile 条件，**不**为此建 `Library/X64/`。

### 4.3 Include 策略（待决）

| 选项 | 说明 |
| ---- | ---- |
| I1 | 保持顶层 `Include/` 按 Abi/Core/Hal/…（现状） |
| I2 | 头文件跟实现走（`30-Core/Scheduler/Scheduler.h`），公开 ABI 另留 `Include/Abi` |
| I3 | 混合：对内私有头跟模块；对外 ABI 集中 |

教学向更易逛的是 **I2（实现旁可见接口）**；开课 ABI 冻结更吃 **I1/I3 的 Abi 集中**。建议：**Abi 集中 + 模块私有头就近**。

## 5. 第四层：模块内按执行顺序分文件夹

示例（示意，非最终名单）：

```text
30-Core/
  10-PhysicalMemory/
  20-VirtualMemory/
  30-Scheduler/
  40-Syscall/
  50-Kernel/            # KernelMain 编排所在
```

Services 同理：

```text
40-Services/
  10-Desktop/
  20-Gui/
  30-Store/
  …
```

规则：

1. 文件夹名 = 模块全词英文（PascalCase 或与现目录一致的一种，**全仓统一**）。  
2. 需要「开机更早」的模块，序号更小。  
3. 同层无依赖的模块：按字母或按产品故事排，**在模块 README 写一句为何排这**。

每个模块目录建议有极短 `README.md`（5～15 行）：人话 + 主文件名 + 依赖谁——可与「人民可读」四块头互补。

## 6. 第五层：主 `.c` + 辅助 `.c`

### 6.1 形状

```text
50-Kernel/                    # 举例
  Kernel.c                    # 主文件：只编排顺序（短）
  KernelModules.c             # 辅：模块表
  KernelModulesInit.c
  KernelModulesInitVideo.c
  …
```

| 角色 | 要求 |
| ---- | ---- |
| 主文件 | 与目录同名或模块名；≤～100～150 行更佳；只调 `InitializeXxx` / 表驱动 |
| 辅助文件 | `主名 + 能力`：`KernelModulesInitVideo.c`；一文件一能力簇 |
| 函数 | 一事一函数；主函数 = 顺序表（见可读性规范 §2.3） |

### 6.2 拆分后如何排序（回应需求 §7「还没想好」）

**观察**：在常见字典序下，

```text
Kernel.c
KernelModules.c
KernelModulesInit.c
KernelModulesInitVideo.c
```

**主文件天然排在最前**（`Kernel.c` < `KernelXxx.c`）。  
因此：**拆分时一律保留主名前缀**，不要拆成无前缀的 `ModulesInitVideo.c`（会漂到别处）。

| 做法 | 结果 |
| ---- | ---- |
| ✅ `Kernel.c` + `KernelFoo.c` | 主文件始终最先 |
| ❌ `Kernel.c` + `Foo.c` | Foo 可能插到无关位置 |
| ⚠️ `Kernel01Foo.c` | 能排，但噪音大；仅当同前缀下能力顺序与字母冲突时再用两位序号 |

**待决细节**：辅文件之间若也要强制执行序（字母不听话），再局部加 `Kernel10Modules.c` / `Kernel20FileSystem.c`；默认先靠「主名前缀 + 字母」足够。

### 6.3 行数门槛（沿用，略收紧主文件）

| 对象 | 建议 |
| ---- | ---- |
| 新辅助 `.c` | ≤300 行（现规范） |
| 主 `.c` | 目标 ≤150；编排用表，不堆逻辑 |
| 函数 | ≤60；对外门面 ≤15；主函数 ≤30 |

文档无行数帽。

## 7. Documents 与 Scripts（需求 §8）

### 7.1 目标

- **全项目只有一处 Documents、一处 Scripts**（或「主入口 + 明确子入口」）。  
- 与 Boot / Kernel **同级**，避免「文档埋在 Kernel 里只有内核作者找得到」。

### 7.2 候选

**D1 — 根级统一（推荐讨论）**

```text
ToyOS/
  00-Documents/          # 现 ToyKernel/Documents + 根说明合并
  01-Scripts/            # 现根 Scripts + ToyKernel/Tools/Scripts 分层说明
  10-Boot/
  20-Kernel/
  …
```

Kernel 内只留极短 `README.md` 指向 `00-Documents/`。

**D2 — 文档仍跟 Kernel，根只留地图**

```text
ToyOS/README.md          # 地图
20-Kernel/Documents/     # 权威文档仍在此
01-Scripts/              # 脚本提升到根
```

- 优点：少搬文档链接。  
- 缺点：外人仍先钻进 Kernel。

**D3 — Documents 按读者拆**

```text
00-Documents/
  ForHumans/             # 人民可读、接手指南
  ForDevelopers/         # 命名、可读性、ABI
  Roadmap/               # 路线图、进展
```

可与 D1 叠加。

**脚本**：构建入口建议固定为根级 `01-Scripts/build-all.sh` 或保留各仓 `build.sh` 但根 Scripts 只做编排。  
**待决**：ToyKernel/Tools 里非脚本工具（字体子集、设计器）算 Scripts 还是 `20-Kernel/Tools/`——建议 **Tools 留 Kernel，Scripts 只放「人要跑的入口」**。

## 8. 命名（需求 §9）

在 [`开发命名规范.md`](开发命名规范.md) 之上，目录树方案再强调：

| 对象 | 要求 |
| ---- | ---- |
| 目录 | 全词；阶段用数字前缀；层名用 Hal/Library/Core… 而非 CodeA |
| 文件 | `模块 + 能力`；主文件 = 模块名 |
| 函数 | PascalCase 全词；层前缀在前（`Hal`/`Kernel`/`Desktop`…） |
| 变量 | 全局 `g`；静态 `s`；局部也尽量见字知意 |
| 禁止 | 拼音标识符；`ktdemo` 类缩写作对外名；目录靠谜语排序 |

与「人民可读」分工：

- **树 + 英文名**：给扫目录、grep、链接器看。  
- **中文人话头**：给打开文件的人看「这是干什么」。  
两套都要，不能互相替代。

## 9. 外部分案摘录（供对照，不照搬）

下列做法来自公开资料，用来**辅助后续设计**，不是 ToyOS 已采纳标准。

### 9.1 操作系统 / 大型系统

| 来源 | 可借鉴点 | 链接 |
| ---- | -------- | ---- |
| [OSDev Wiki · Code Management](https://wiki.osdev.org/Code_Management) | **arch 与可移植代码分开**；树布局一致比个人偏好重要；接口命名先于实现细节 | osdev.org |
| Linux 源码地图 | 顶层按子系统（`kernel/` `mm/` `fs/` `drivers/` `arch/`）；arch 单独一枝；可移植层不复制三份 | 各类 Linux 导读 |
| [Fuchsia 源码布局](https://fuchsia.googlesource.com/fuchsia/+/HEAD/docs/development/source_code/layout.md) | 递归「area」：每区职责清晰、自带文档与测试；命名短而稳定 | fuchsia.dev / googlesource |

### 9.2 工程目录习惯

| 来源 | 可借鉴点 | 链接 |
| ---- | -------- | ---- |
| [Folder-Structure-Conventions](https://github.com/KriaSoft/Folder-Structure-Conventions) | 顶层常见：`src` / `docs` / `build` / `tools`；**短名、一致** | GitHub |
| [Frogtoss Native Project Standards](https://www.frogtoss.com/labs/pages/native-project-standards.html) | 源码与发布根**并列**；文件名前缀优于过深目录，便于字母序浏览 | frogtoss.com |
| [P1204 Canonical Project Structure](https://open-std.org/JTC1/SC22/WG21/docs/papers/2018/p1204r0.html) | 头与源就近；路径即逻辑名；避免随意特殊字符 | open-std.org |

### 9.3 可读性与风格（代码本体）

| 来源 | 可借鉴点 |
| ---- | -------- |
| Dijkstra 风格指南类文档 | 名字揭示意图；目录按**职责**不按实现噱头；少写复述型注释；架构文档先写意图再写结构 |
| Clean Code / 类似实践（行业常识） | 小函数、少副作用、编排与实现分离——与本仓「主文件顺序表」一致 |
| 教学 OS（xv6 等）常见做法 | 树浅、文件少、每文件开头一段「本章干什么」——接近「人民可读」四块头 |
| 本仓已有 | 顺序表不进策略；平台三路分发；人话头；≤300 行拆文件 |

### 9.4 可直接变成 ToyOS 细则的启发

1. **数字前缀解决字母序 ≠ 依赖序**（本方案核心，业界少写进规范但桌面浏览极常用）。  
2. **arch 只出现一次枝**（OSDev / Linux），Library 以下永不叉开。  
3. **主名作文件前缀** 保证主 `.c` 排最前（Frogtoss「前缀优于深目录」的变体）。  
4. **每个 area 自带短文档**（Fuchsia），降低对路线图考古的依赖。  
5. **改布局与改行为分 PR**（本仓协作暗号已具备 TG/JX）。

## 11. 建议落地节奏（仅选型，不开刀）

| 阶段 | 内容 | 破 ABI？ |

> 接下来我们将讨论一件很严肃的事情，就代码可读性这方面，刚才做得还差很远。我需要做到的是：  
> 1. 最外层是 ToyOS，进入以后看到的文件夹，按字母排列的顺序，就是从开发到编译到运行的三个阶段，从 boot 到 kernel 到 build 到 image，不过这四个词目前排序不符合前面所说的；

> 6. 到最底层的文件夹里面可能都是 `.c` 文件了，需要满足一个主 c 文件，+ 若干辅助文件的结构，主 c 文件排在最前，负责编排执行顺序，功能放在辅助文件里，所以主 c 文件一般不大；  
> 7. 一个文件一个功能，一个函数做一件事。如果单文件太大，则按照主文件前缀拆分，比如 `Kernel.c`，`KernelFileSystem.c` 这样拆分，但是如果文件也需要按顺序排列，那不一定好排，我还没想好；

> 9. 文件名、函数名、变量名等按照自说明的方式命名，不怕长，但是要讲清楚自己是干什么的，哪个模块的；

### 13.1 补充（模块化 / 四层驱动）

> 另外我还想做到更加模块化，比如我加一个硬件型号，它应该归为某一类，像 intel 的某个网卡，它应该是增加一个自文件夹就行了，具体的型号不应该和更上层的文件代码混在一起。我跟 deepseek 讨论过一个 4 层的驱动模型，你了解吗？除了驱动外，其他的模块我也是想这样做，替换模块就是换掉一个文件夹或者新增一个文件夹，这就要求各个模块之间的契约要定好。像是 HAL.H 这种，头文件定好，但是具体实现都是可替换的。

### 13.2 四层驱动定名（采纳）

## 15. 模块化：契约与四层驱动模型（草案）

### 15.0 一句话

**契约头稳定；实现按 Class → Protocol → Family → Chip 分夹，可增可换。**  
加一款网卡：多数时候只动 **Family 夹**（新族）或 **Chip / quirks**（同族新型号），不改 `Hal.h`，不改 Desktop，不把芯片细节写进上层。

**权威四层 = §15.1（已采纳）。**  
`Hal.h` / Backend / `*_OPS` **不是**四层之一，而是压在四层之上的**横切契约**（§15.4）。

### 15.1 四层驱动（已采纳）

从上到下 = 越来越「认具体硅片」；依赖只允许**向下**。

```text
第一层  Class（设备类）
        Block / Input / Net / Display / Audio
              ↓
第二层  Protocol（协议 / 接口）
        例：Net → NicL2（以太网 L2）
        不是所有 Net 都是以太网；ToyOS 现在只有以太网
              ↓
第三层  Controller Family（控制器族）
        例：E1000 / Rtl8169 / Alx / Iwl
        同族：寄存器布局、描述符格式大体相同
              ↓
第四层  Chip / Model（具体型号）
        例：82540 / 82574 / I219 / Rtl8168 / Rtl8111 / Ar8161 / 8265
        同族差异 → quirks 表，而不是复制一整份驱动
```

| 层 | 人话 | 改这里的时机 | **禁止**出现在这一层 |
| -- | ---- | ------------ | -------------------- |
| 1 Class | 这是哪一类外设 | 新增大类（少见） | 某芯片寄存器、某族描述符 |
| 2 Protocol | 这类外设讲哪种「话」 | 同类下第二种协议（如 Net 将来非以太网） | E1000 私货；Services UI |
| 3 Family | 同一套控制器编程模型 | **新控制器族**（加文件夹主战场之一） | 把单型号 quirk 写进族公共路径且无表 |
| 4 Chip | 这一颗具体料 | **同族新型号**（quirks 行或薄型号文件/夹） | 改 Class/Protocol 契约；include Services 私头 |

**总线（PCI/USB/Virtio）放哪？**  
总线是**发现与资源**手段，不是这四层里的一层。Probe/Match 可放在 Family 入口，或单独的 `Bus/` 工具夹供各 Family 调用——**不**插进 Class/Protocol 之间冒充第二层。

### 15.2 加硬件时动哪一层（人话清单）

| 场景 | 动哪 | 例子 |
| ---- | ---- | ---- |
| 同族新 stepping / 新 PCI ID | **第 4 层**：quirks 表加一行（或薄 Chip 文件） | E1000 族加 82574 |
| 新控制器编程模型 | **第 3 层**：新建 Family 文件夹 | 新增一个从未支持过的 NIC 族 |
| 同类但协议不同 | **第 2 层**：新建 Protocol 夹 | Net 下除 NicL2 外再加别的 |
| 全新大类 | **第 1 层**：新建 Class 夹 + 契约 Backend | 若尚无某 Class |

上层（Core / Services / 桌面）在以上场景下都应 **零改**，或仅经契约扩展（罕见）。

对照现网：

- [`驱动开发指南.md`](../驱动/驱动开发指南.md)「一设备一夹」≈ 今日多落在 **Family**（`E1000/` `Iwl/`…），Chip 尚未普遍拆出。  
- [`模块化与App课堂闭环.md`](../待做/模块化与App课堂闭环.md) 同方向；本 § 把「夹」细成四层尺子。  
- `Drivers/Net/` 今日偏 **Class + 部分 Protocol 胶水**；终态应明确挂在 `Net/NicL2/` 下。

### 15.3 目录示意（Net / 以太网）

**目标形状（严格嵌套，讨论稿）**：

```text
Drivers/
  Net/                      # ① Class
    NicL2/                  # ② Protocol（以太网 L2；今日唯一）
      E1000/                # ③ Family
        E1000.c             # 族公共：描述符、主流路径
        E1000Quirks.c       # ④ Chip 差异表（82540/82574/I219…）
        # 或：82574.c 薄文件，只填 quirk / 小差异
      Rtl8169/
      Alx/
      Iwl/                  # Wi‑Fi 若协议不同则另开 Protocol；暂挂须在 README 标明
    # NicWifiMgmt/          # ② 将来示例，未建
  Block/
  Input/
  Display/
  Audio/
  _template/
```

**较浅形状（迁移友好，可选过渡）**：

```text
Drivers/
  Net/
    NicL2/
      E1000/                # Family = 一夹；Chip 只活在 quirks 表，不建子目录
      Rtl8169/
```

待决见 §12 问题 10：第四层是**目录**还是**表**。  
经验规则：**差异小 → quirks 表；差异大到几乎两套路径 → 才建 Chip 子夹或新 Family。**

### 15.4 横切契约（不是第五「驱动层」，但是硬边界）

```text
        Core / Services / 用户可见能力
                 │  只依赖契约头
                 ▼
        ┌────────────────────┐
        │ Contract（横切）    │  Hal.h / 类 Backend / 协议 Ops
        └────────────────────┘
                 │
                 ▼
        Class → Protocol → Family → Chip
```

| 契约形态 | 已有范例 | 谁实现 | 谁调用 |
| -------- | -------- | ------ | ------ |
| 平台门面 | `Hal.h` | 各 arch Hal 夹 | Core / Services |
| 类 Backend | `NET_BACKEND` / `INPUT_BACKEND` / Block… | 通常 **Family** 汇总实现 | 设备框架 / Protocol |
| 协议 Ops（可增） | 将来 `NIC_L2_OPS` 一类 | Family | Protocol 胶水 |
| 政策 `*_OPS` | `SCHEDULER_OPS` 等 | Modules 下各夹 | Core 框架 |

规则：

1. 契约头在 `Include/`（或模块公开头）；**不出现** Chip 名作 API。  
2. Family/Chip **不得**把私货类型塞进契约头。  
3. **替换 Family** = 换/加文件夹 + 注册；**替换政策模块** = 换 Modules 下文件夹。  
4. Services **禁止** `#include` Family/Chip 私头。

### 15.5 非驱动模块：同一套「换夹」

驱动按四层加硬件；调度/内存/FS 按「契约 + 实现夹」换政策（不必硬套 Chip 四层，但**语感一致**）：

```text
35-Modules/
  Scheduler/
    RoundRobin/
    Priority/
  PhysicalMemory/
    Bitmap/
    BestFit/
  FileSystem/
    Fat/
    Ram/
```

| 动作 | 驱动 | 政策模块 |
| ---- | ---- | -------- |
| 新增 | 新 Family 夹，或同族 Chip/quirk | 新政策夹 |
| 替换 | 注册/绑定另一个 Family | `SCHEDULER=` / `MEMORY=` / `FS=` |
| 契约 | Backend / 协议 Ops / `Hal*` | `*_OPS` |
| 框架留下 | 枚举、类 Attach、锁与表 | 队列骨架、段表、VFS 外壳 |

**目标语**：说「可替换」= **指得到契约头 + 指得到被换的文件夹（或 quirk 行）**。

### 15.6 可读性上多赚到什么

| 没有这四层时 | 有 Class→…→Chip 时 |
| ------------ | ------------------- |
| Intel 网卡细节和「网卡类」糊在一起 | 进 `Net/NicL2/E1000/` 只看一族 |
| 新型号复制整文件 | 多数只加 quirk 一行 |
| 将来非以太网 Net 无处安放 | 在 Net 下加新 Protocol 夹 |
| 换学生调度器改框架中段 | 只换 Modules 里一个夹 |

### 15.7 非目标（本期写死）

- 不做完整 PnP / 用户态可加载驱动。  
- 不要求存量驱动一夜搬成四层嵌套（分刀审计）。  
- 不在 `Hal.h` 为每个 Chip 加 `#ifdef`。  
- 不把 PCI/USB 总线冒充成第二层 Protocol。  
- Wi‑Fi（Iwl）最终归 NicL2 还是独立 Protocol：**另议**，先允许挂现网能跑的位置并在 README 标明。
